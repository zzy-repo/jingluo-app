## 一、#32 直链导入暂存报「文件内容不完整」

### 1.1 可验证断言

用户看到的第一条结论是「同一份包、带了图片就整包失败」，第二条是「下载少字节也会走到同一句文案」。断言拆成两条可独立验证的：

- A（下载段）：响应既无 `Content-Length` 也无 `Content-Range`（chunked-transfer、中间设备剥头）时，分块下载循环把「比请求短的一块」当成「最后一块」，于是**被截断的包被当完整文件交出**。
- B（导入段）：条目顺序为「图片先于其所属会话 JSON」，或多出一个没有会话 JSON 的孤立图片目录时，**整包被判「文件内容不完整」**，而注释声明支持这种顺序。

### 1.2 复现 A：真实 HTTP 服务 + 真实下载循环

`_scratch/repro-32-download.mjs` 起本地 `node:http` 服务，`CapacitorHttp.get` 用 `fetch` 打到它（`connectTimeout`/`readTimeout` 只对原生生效，本地桩忽略，不影响判定逻辑）。包体 307 200 B，ZIP magic 合法。

实测输出（逐字）：

```

    字节: 交出文件 307200 B / 服务端共 307200 B

### chunked-truncate  (33ms)
    结果: 下载阶段放行（进入 importHistory）
    字节: 交出文件 184320 B / 服务端共 307200 B

### chunked-error  (330ms)
    结果: BackupError historyImportUrlNetwork「下载失败，请检查网络连接后重试」
    字节: 未交出文件

    字节: 未交出文件
```

`chunked-truncate` 是缺陷本体：服务端只给 60%（184 320 / 307 200 B）且不给长度头，下载循环**当作下载完成**放行。其余四组说明已有的三道防线都有效：声明了长度却断链 → `historyImportUrlNetwork`；中途丢 Range → `historyImportUrlBadResponse`；断链被传输层报错 → 同样归到 network。也就是说**缺的只是「没有任何长度证据」这一条分支**。

### 1.3 复现 B：真实导入链路 + 八种包形

### 1.4 三方结论

| 断言 | 结论 | 依据 |
| --- | --- | --- |
| A 无长度证据时截断包被放行 | **确实失败** | `chunked-truncate` 交出 184 320/307 200 B 并进入 importHistory |
| B 图片顺序/孤立目录导致整包失败 | **确实失败** | B/C/D/G 全部 `backupIncomplete`，同一包换顺序即通过 |
| 下载有长度头时的完整性校验 | **通过** | `full`/`declared-truncate`/`range-lost` 三组均正确终止 |
| ZIP 非包与格式错误分类 | **通过** | F → `backupUnrecognized`（与 #40 的日志同一句，属 #40 范围） |
| 线上真实用户包是否就是交错顺序 | **不可判定** | 需拿到 #40/#50 归档实包；本机不能下载用户包 |

> 与 #40 的边界不变：真实用户那批日志是 `bytes == download.total`、失败在 `check` 阶段的 `backupUnrecognized`（「无法识别该文件…」），那是 #40。本单两条缺陷的文案都是 `backupIncomplete`（「文件内容不完整，无法导入」），不要合并。

### 1.5 根因（file:line）

**A（下载段）** `src/services/chat/history/urlImport.ts`

- `:719` `if (status === 200 || bytes.byteLength < requested) break` ——「不足请求的一块 = 已经是最后一块」这个前提只在服务端返回过长度时成立。
- `:731` `if (state.total !== undefined && state.downloaded < state.total)` —— `state.total` 只可能来自 `contentRangeTotal()`（需要 206 + `Content-Range`）或 `contentLength()`；两者都缺时**整个完整性校验被跳过**。
- `:682` `state.total` 赋值处：`contentRangeTotal(response.headers) ?? contentLength(response.headers)`，chunked 响应两者皆空。

**B（导入段）** `src/services/chat/history/importArchive.ts`

- `:146-156` 图片归属判定：`index` 未出现时只认 `currentSessionId && path.startsWith(sessionFilesDir(currentSessionId))`；图片排在其会话 JSON 之前时 `currentSessionId` 还是上一个会话（首张图时为 `undefined`），落到 `:155` `fail('backupIncomplete')`。
- `:87` 头注释写着「也支持会话与图片交错排列、index 位于末尾的条目顺序」——声明与实现不一致。
- `:148` `imported.has(/^chat_sessions\/([^/]+)_files\//.exec(path)?.[1] ?? '')`：`index` 已读到时，孤立图片目录（无对应会话 JSON）同样落到同一个 `fail`。
- 文案来源：`src/i18n/zh.ts:96` `backupIncomplete: '文件内容不完整，无法导入'`（`en.ts:101` 同）。

### 1.6 修复方案

#### A 下载段：没有长度证据就不许判完成

1. `:719` 的结束判定改为「只有拿到**终止证据**才算结束」：`416`（请求起点超出末尾）或 `bytes.byteLength === 0`。`bytes.byteLength < requested` 在 `state.total === undefined` 时**不再 break**，而是继续按原块大小请求下一块。
2. 连续 N 次（建议 2）拿不到终止证据且总字节不再增长 → 按「链路中断」终止：`recordDownloadFailure('unverified-length', ...)` + `fail('historyImportUrlInterrupted', {})`（百分比未知时不传），可点重试。
3. `Content-Length`/`Content-Range` 双缺时在 `import: download archive` 埋点里补一个 `'download.lengthKnown': false`，让下一批日志能直接分辨这类响应。
4. 有长度头的老路径（OBS 常态 206 + `Content-Range`）行为不变，仅多一次 416 探测。

- **影响面**：只动 `downloadArchive` 的循环终止条件。取消失效、120 s 总预算、心跳、`range-lost`/`tooLarge`/`notZip` 分类全部不动。
- **回归命令**：
  - `env -u http_proxy -u https_proxy -u HTTP_PROXY -u HTTPS_PROXY pnpm test`（含 `tests/unit/url-import-stall.test.mjs`）
  - `pnpm test:integration --only url-import-stages`
  - `node --experimental-transform-types --import ./_scratch/register.mjs _scratch/repro-32-download.mjs`（六种响应，`chunked-truncate` 必须从「放行」变成 `historyImportUrlInterrupted`）
- **未测边界**：真机 OkHttp 在 chunked + 无长度头下的实际行为；服务端持续返回短 206 且永不返回 416 的病态实现；>200 MB 包的预算与内存。**待真机证据。**

#### B 导入段：图片条目归属改为「先登记、后回填、无主则跳过」

1. `:146-156` 改成分两支：
   - 能立刻确定归属（`images.get(path)` 命中且会话已导入）→ 现状不变；
   - 否则按 `sessionId` 记入 `pendingImages: Map<string, string[]>`，会话 JSON 到达时回填并把该目录下已登记的条目补存。
2. 条目流结束仍无归属 → `skipEntry`（已读完，CRC 与大小照样校验）+ `recordEvent('import_stage', 'import: skipped orphan image', { 'entry.path': path })`，**不再整包失败**。与 `paths.ts` 的「未被引用的条目不保存」保持同一策略。
3. 保持收紧的不变项：`manifest` 必须在首位、会话 JSON 自身 id 必须等于路径 id 且不重复（`:123-136`）、`index` 与 `imported` 集合必须一致（`:166-173`）——结构性错误仍然整包失败。
4. 文案分流：`backupIncomplete` 只留给上述结构性错误；条目级跳过属于「部分导入」，走 `onProgress` 计数而不是报错。

- **影响面**：只放宽条目归属；暂存写入量不变（跳过的条目依旧读完校验 CRC）；`db.addStagingSession`/`saveStagingFiles` 调用序不变。`MAX_ARCHIVE_BYTES`、取消语义不变。
- **回归命令**：同上 `pnpm test` / `pnpm test:integration --only url-import-stages`，加
  `node --experimental-transform-types --import ./_scratch/register.mjs _scratch/repro-32-import.mjs`
  （A/B/C/D/G 应全部 `staging: PASS`，E/F 的结论不变）。
- **未测边界**：40 会话 / 512 KiB（21 MB）真机全量导入的耗时与内存；#50 的三包 A/B 未做——**顺序上应先做 #50**，用线上实包确认「交错顺序」是否真是线上包形，否则本条只是修好了 fixture 与自家导出的包。**待真机证据。**

## 二、#14 原生桥挂死、界面无限转圈

### 2.1 可验证断言

- 断言 1（静态）：出问题的那版构建里，`await requestRange(...)` 没有任何上限，15 s 看门狗只写日志、不中断、不产生终态。
- 断言 2（运行）：当前 main 在原生 Promise 永不 settle 时，120 s 内必定给出终态并落 `import_error`，且周期心跳可见。

### 2.2 复现：永不 settle 的原生桥

`_scratch/repro-14-hang.mjs`：`CapacitorHttp.get` 返回 `new Promise(() => {})`（永不 resolve/reject），走真实 `importHistoryFromUrl`。`out-14.log` 摘录（逐字，节选）：

三点实证：心跳 5 s 一次且带 `attempt`/`from`/`span`/`budget.leftMs`（正是 #14 要求的字段）；120 s 硬终态；`still-pending-native-promises = 1` 说明原生 Promise 至今仍悬着——**印证 `SettingsDialog.tsx:835` 的判断：CapacitorHttp 不能 abort，只能不发新块、不再采用它的返回值**，JS 侧墙钟预算是唯一终态来源。

### 2.3 静态根因链（出问题的那版构建）

`git show a2290c5:src/services/chat/history/urlImport.ts`，逐字：

```
401:    const silentTimer = setTimeout(() => {
402:      recordEvent('import_stage', 'import: native request silent >15s', {
411:      const response = await requestRange(url, from, from + span - 1)
412:      clearTimeout(silentTimer)
423:      clearTimeout(silentTimer)
```

`sitentTimer` 只 `recordEvent`，`await requestRange(...)` 本身没有 race、没有 abort、没有超时兜底，因此原生 Promise 不 settle 时整个 `fetchChunk` 永久挂起，下载循环也不会进入下一轮 → 没有任何终态、没有心跳、没有 `import_error`。这与票据 `1244ad5c` 的现象完全吻合：第一条 `native request begin` + `native response (206)` 之后彻底静默 15 分钟，而用户还能点「复制详情」「展开」，说明主线程活着、只是那条 Promise 死了。

当前 main 的替代实现（同一文件）：`DOWNLOAD_TOTAL_BUDGET_MS = 120_000`（`e5c78fd:56`）、`withinBudget(...)`（`:363`，调用点 `:557`）、`startDownloadHeartbeat(...)`（`:423`，调用点 `:645`）、终态分类 `:751-772`。

### 2.4 三方结论

| 断言 | 结论 | 依据 |
| --- | --- | --- |
| 断言 1：出问题版本无限挂起 | **确实失败**（静态证明） | `a2290c5:401-412` 无任何中止手段 |
| 断言 2：当前 main 有界 | **通过**（运行证明） | 120 017 ms 拿到 `historyImportUrlStalledUnknownTotal` + `import_error` |
| 「错误面板渲染却不落 `import_error`」 | **通过**（不再是缺陷） | 有终态就有 error：`urlImport.ts:866-874` / `backup.ts:78-87` 必录；旧构建是「没有终态可报」，不是「没上报」 |
| 真机上 beta.8 用户那次挂死是否同一根因 | **不可判定** | 需 beta.9+ 真机长跑证据；票据里那条日志停在 206 响应后，也可能卡在原生返回后的第一轮循环调度上。**待真机证据。** |

### 2.5 修复方案（补完剩余无兜底的原生调用）

主体修复已随 `e5c78fd` 在 main 上，本单剩下的是**同类漏点**：

1. 抽出通用函数 `withBudget<T>(work: Promise<T>, ms: number, onExpire: () => T | never)`（`withinBudget` 已经是它的特例），给这些调用点补兜底：
   - `src/services/chat/backup.ts` 的 `importHistory`：`check` 与 `staging` 两阶段各加 wall-clock 预算（建议 60 s / 180 s），超时 → `BackupError('backupIncomplete' 之外的专用 key)`，让「卡在解析」也有终态；
   - `src/services/exportText.ts`：`writeChunk` 循环（`CHUNK_BYTES = 48 * 1024`）每次调用加 10 s 预算，超时 `bridge.abort()` + 报错；
   - `src/services/appUpdate.ts:34`、`src/services/diagnostics/collector.ts:521`：`registerPlugin` 调用加一次性 15 s 预算（低危，观测不到就当失败）。
2. 所有看门狗触发时统一落一条 `record('import_error', 'error', 'watchdog fired', { phase, budgetMs })`，便于下次拿日志直接定位。
3. UI 兜底：错误面板每次渲染时补一条 `record('import_error', 'error', 'error panel shown', { phase })`，防止将来再出现「有面板无日志」。

- **影响面**：新增预算只影响失败路径的终止时机；`download` 阶段既有 120 s 预算与心跳不变；`exportText` 增加 abort 调用点（原生 `abort` 已存在）。
- **回归命令**：`pnpm test`（`tests/unit/url-import-stall.test.mjs` 是同类先例）；`node --experimental-transform-types --import ./_scratch/register.mjs _scratch/repro-14-hang.mjs`（须在 ~120 s 内出终态）；导出链路用现有人工用例复跑。
- **未测边界**：真机上 `writeChunk` 挂死的复现（需构造原生侧阻塞）；预算值与弱网实际耗时的匹配（120 s 是否够 20 MB 弱网下载）。**待真机证据。**
