## 1. 替代验证路径：谁能跑 / 跑什么 / 贴什么

### 1.1 先分清「哪一层能用本地替代」

| 线 | 覆盖什么 | 谁能跑（前置） | 本地能不能等价 | 在哪一节 |
| --- | --- | --- | --- | --- |
| **A 线：发布与仓库卫生** | 8 道门禁（引用/行尾/卫生/私有发布根/签名配置/发版自检/截图引用/阈值收敛） | 任意装了 **Node ≥ 22** 的机器；**不需要浏览器、不需要 JDK**（`check:keystore` 走 `--config-only` 降级档）、不需要网络 | **能**（本轮 8/8 实测） | §1.2 |
| **通用代码层** | `tsc` / `oxlint` / `unit` | 同上 + 已装依赖（`pnpm install`） | **能，但有超时盲区** | §1.3、§2 |
| 产物 / 截图 | `check:ui-shots` 只验「引用指得着」，不验像素 | 同上 | 部分 | §1.2 |
| **L1 集成层 6 分片** | 域主路径（真实浏览器 + 静态服务 + 容器） | 需要容器化 Playwright 与 dist 产物 | **不能** | 等云端 |
| **flaky 三态 / 跨 runner** | 跨 runner 判据（需要两台 runner 的历史记录） | 需要多台机器 + 累积记录 | **不能** | 等云端 |
| gradle / APK 产物 | 出得了包 | JDK 21 + Android SDK | 部分（有 SDK 的机器能跑） | 等云端或本机出包 |

**这张表的意义：说清「本地绿」覆盖到哪一层就停。** 拿 §1.1 上半部分的绿去替代 `integration`
是无效替代 —— 它们验的根本不是同一件事。**「不能等价」不是「可以不算」，而是「必须进补跑清单」**（见 §3.3）。

### 1.3 通用代码层三条

```bash
npx tsc -p tsconfig.json                  # = pnpm run type（CI 的 "Type check" 步）
npx oxlint src                            # = pnpm run lint（CI 的 "Lint" 步）
node tests/run-layer.mjs unit             # = pnpm test（CI 的 "Unit tests" 步）
```

本轮实测：`tsc` exit 0（无输出即通过）；`oxlint` `Found 0 warnings and 0 errors. … 278 files`、
exit 0。`unit` 整层的结论**必须按 §2 读**——它在慢机器上会给出「合法自检被判超时」的假红。

### 1.4 证据格式：贴什么才算数

**每条证据 = 命令 + 最后一行输出 + exit code，三样缺一不可。** 不许写「应该没问题」「本地测过没问题」——
这两句话无法复核，等于没写。

模板（照抄）：

````text
$ node scripts/check-eol.mjs
check:eol OK —— 扫描 1307 个会进仓库的文本文件（git 跟踪 + 未跟踪未忽略），无 CRLF 行尾
exit=0
````

另外四条硬要求：

1. **写清在哪个 commit 上跑的**（`main@253dae31` 这种写法），不然「本地绿」对不上任何东西；
2. **写清 worktree / 是否干净**（`git status --short` 的输出为空，或者把脏的那几行贴出来）；
3. **跑的是脚本原文，不许改判据、不许加 `--skip` 类开关**（#651 明令，见 §4.3）；
4. 输出很长时贴**最后一行**（判定行）+ 完整日志落到临时目录的路径，别贴中间过程。

## 2. 本地等价验证的已知盲区（**别让后人误判**）

### 2.1 `tests/unit/gate-negative-controls.test.mjs` 贴着超时上限

这一个是**最容易被误判成「代码红」的地方**，实测两轮：

| 跑法 | 结果 | 墙钟 |
| --- | --- | --- |
| **单跑**（`node tests/unit/gate-negative-controls.test.mjs`） | `pass 15 / fail 0`（`tests 15, cancelled 0, skipped 0, todo 0`） | **340.1s** |
| **经 runner**（`node tests/run-layer.mjs unit`，默认 `--timeout-ms 180000`） | `<< TIMEOUT tests/unit/gate-negative-controls.test.mjs (180058ms)` → `Total 1: PASS 0, FAIL 1 … elapsed 360404ms` | **360.4s**（两次 180s） |

**注意 runner 那一行是「超时」不是「断言失败」**：它先 `✖ … (179697.831831ms)`、
`Promise resolution is still pending but the event loop has already resolved`，
再按 flaky 判据**自动重跑一次**（`↻ 红了（180070ms），按 flaky 判据重跑一次…`），
第二次同样被停掉，才落成 `<< TIMEOUT`。**超时是确定性的，重跑只把 180s 变成 360s，不会变绿。**

（另一台机器上的同口径实测是 `15 pass / 0 fail`、**230.8s** —— **两台机器的绝对值不一样，
但都超过默认 180s**；所以这条盲区跟机器快慢无关，只跟「它是不是贴着上限」有关。）

本机单跑的分拍耗时（说明「慢在哪」）：

| 拍 | 耗时 | 拍 | 耗时 |
| --- | --- | --- | --- |
| N3 `build`（rspack 临时副本） | 99.4s | N4 `check:test-layout` | 31.0s |
| N2 `lint` | 60.3s | N1 `type` | 18.7s |
| N7 `test:dl-release` | 58.8s | N5 `check:test-duplication` | 15.8s |
| N8 `check:keystore` | 39.0s | N10 `check:capabilities` | 12.5s |

**判读规则（照这个顺序看，不要跳步）：**

1. 看到它红，**先看是不是 `<< TIMEOUT`**（runner 的判定行），而不是断言失败 ——
   `<< TIMEOUT` 意味着「进程被停掉，断言根本没跑完」，**这不是代码红**；
2. 是超时 → 用 `--timeout-ms 300000` **单独**跑它（`node tests/run-layer.mjs unit --only gate-negative-controls --timeout-ms 300000`）；
3. 还是超时 → 才怀疑代码；仍未超时但变红 → 那才是真红，按 `docs/TESTING-POLICY.md` §6 记「命令 + 最后一行 + 时间戳」并开单。

**根治方向（两条，都不动断言）**：
- **a.** 给 CI 的 unit 步显式抬 `--timeout-ms 300000`（与 L1 分片的 420000 同风格）；
- **b.** 把它拆小：N3 / N7 / N2 这类重拍（99s / 59s / 60s）拆成独立文件，让主文件回到 60s 内。

### 2.2 口径：**「本地 unit 全绿」不能当唯一判据**

两个方向都会错，必须一起写清楚：

- **本地红 ≠ 代码红**（§2.1：超时被当成失败）；
- **本地绿 ≠ CI 会绿**（本机比 CI 慢 ⇒ 本机绿说明有余量，但反过来，本机绿**不能证明**
  CI 的 `golden` / `integration`×6 会绿 —— 那两层本地根本跑不了，见 §1.1）。

所以「本地等价验证」的结论要写成**分层的**：
「A 线 8/8 绿 + type/lint 绿 + unit 除超时外全绿（超时项单跑 15/15 绿）」，**再加上**一句
「`golden` / `integration`×6 / `flaky` 未验，已进 §3.3 补跑清单」。**缺最后这句就是假绿。**

## 4. 这段期间的合并纪律（写给后来人）

### 4.1 破例的三个条件（缺一不可）

只有在**同时**满足这三条时才允许在「云端不跑」的状态下合并：

1. **内容等价已验证**：本地跑过与被改文件相关的层（纯文档 → §1.2 的 8 道；代码 → §1.3 + 相关层），
   并贴了「命令 + 最后一行 + exit」；
2. **破例理由写在 PR 正文里**：一句话说明为什么这次不能等（例：
   「计费停摆，9 job 零步，本地 8/8 门禁绿，等恢复会阻塞 #xxx」）；
3. **留痕**：PR 正文 + 车道单（#651 / #652）各记一笔，恢复后在 §3.1 台账里能查到。

### 4.2 风险分级：纯文档可以走破例，代码 PR 必须本地跑过对应层

| 改动类型 | 破例可否 | 最低验证 |
| --- | --- | --- |
| **纯文档**（只动 `docs/**`、`CHANGELOG.md`） | **可以** | §1.2 的 8 道全绿（本轮实测 8/8） |
| 纯用例（只动 `tests/**`） | 谨慎 | `unit`（或 `integration`）+ 负向对照，且**必须排除 §2.1 的超时假红** |
| 代码（`src/**`、`shared/**`、`config/**`） | **不建议**，需要更强理由 | §1.3 三条 + 受影响层；改了行号还可能打破文档引用（见 §3.4） |
| workflow / CI / 设置 | **不许** | 改门禁本身在门禁失灵期间改，等于没人验门禁 |

### 4.3 不许为了「看到绿」动判据（#651 明令）

- 不许改断言、不许加 `--skip` / `--only` 之类的绕过开关、不许把门禁从 `ci.yml` 摘掉；
- 不许把「超时」改判成「跳过」（§2.1 那条：抬 `--timeout-ms` 是**换配置**，
  `docs/TESTING-POLICY.md` §6 允许并要求写明换了什么；`skip` 不是）；
- 不许把「9 job 零步」解释成「基础设施问题所以不用验」—— **零步 = 没验**，进 §3.3。

### 4.4 恢复当天的第一件事

不是补发布、不是重跑历史 run，而是**把 `main` 的最新一次跑绿**（§3.3 第 1 步），
然后按台账逐条补跑。历史 run 不必全量重跑：**重跑会再计分钟**，
`gh run rerun <run-id> --failed` 只对「最新 main + 当前 open PR 的 head」用（口径同 #723 §5）。
