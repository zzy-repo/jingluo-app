**一句话结论**：没有找到「不付钱直接拿卡密 / 直接改单为已支付」的通道——`/notify` 有签名校验、`/buy` 强制 `cid`、`order_token` 强制校验、plan 价格完全服务端定价、`/api/orders` 严格按 Key 反查。真正的风险集中在**身份层**：`device_id` 被当成账号的唯一凭据，既没有二次认证、又在明文 HTTP 上传输，并且**邀请池与支付服务是两套互不相认的身份库**，同一条 `device_id` 能拿到两个账号、两份新人额度。这三条共同放大了 #243 / #135 / #157 的实际可利用性。

## 2. 关键实测事实（后文引用的原始观察）

1. `GET /api/plans` → 200，`newbie`「新人特惠 1 元额度」`price=1.0 / points=500`。按 100 积分 ≈ ¥1，¥1 买 500 积分＝**面值 5 倍**，这正是 #135 的套利动机。
2. `POST http://62.106.70.167:60013/apply {device_id}` → 201，返回 `customer_id`、`invite_code`、`quota_points=100.0`、`remaining_points=100.0`、**明文 `key`**。同 `device_id` 重放 → 200，Key 与额度不变（幂等）。
3. 同一 `device_id` 在 `https://apia.ecsafe.cn/invite/apply` → 201，**`customer_id=19`**（另一套编号），同样给 100 新人积分、另一个 Key。
4. `POST /rotate {device_id}`（**不带任何 Key**）→ 200 `rotated:true`、`previous_key_id:141`、返回新的可用 Key。apia 域 `/invite/rotate` 同样成立。
5. `https://apia.ecsafe.cn/me?device_id=…` → 404「路径不存在」；`/invite/me?device_id=…` → 200，返回该设备的 `customer_id`、`invite_code`、`remaining_points`、`key_status`（**无需任何 Key**）。
6. `device_id` 大写变体：`/me` → 404 `device_not_found`；`/apply` → **201，`customer_id` 24 → 25，再给 100 新人积分**。
7. `device_id` 带尾随空格 → 400 `bad_device_id`（客户端 `isDeviceId` 先 trim，服务端也校验字符集）。
8. `GET /buy?plan=p1`（无 `cid`）→ 400「请先在 App 内领取 Key，再回来购买」；`cid=0/-1/abc` → 同上 400；`cid=999999999` → 400「客户不存在」；`cid=19`（自有）→ 302。
9. 302 `Location` = `https://pay.xiaodouap.cn/submit.php?pid=…&out_trade_no=CP2026111911…F63A&money=1.00&sign=<MD5>&sign_type=MD5&return_url=…%3Fno%3D…%26order_token%3D<16 位>…`。
10. `/api/order?out_trade_no=…&order_token=<正确>` → 200，`status=pending`、`amount_fen=100`、**回显 `customer_id`**；token 错误 → **403** `UNAUTHORIZED`「订单凭证不匹配」；token 缺失（该单真实存在）→ 403；`out_trade_no` 不存在 → **404** `ORDER_NOT_FOUND`。
11. `POST /notify` 空 body → **400 `bad sign`**；完整参数 + 伪造 `sign=000…0` → **400 `bad sign`**；该单事后仍为 `pending`。
12. `GET /return?no=…&order_token=…` → 200，静态 HTML「支付处理中」，不改变任何状态。
13. 兑换池 `/redeem-card`：`card_no` 不存在 → 404 `card_not_found`，**无论 `api_key` 有效（自有 Key）、无效（`sk-live-deadbeef…`）还是缺省都先报卡号不存在**。
14. apia `/api/redeem`：`card_no` 不存在 + 有效 Key → 404 `CARD_NOT_FOUND`；**假 Key → 400 `API_KEY_INVALID`（先验 Key）**；同 `request_id` 重发 → 同样 404（无幂等痕迹可观测）。
15. 限流：`/buy` 连发 12 次 → 第 1–10 次 302，**第 11、12 次 429** `RATE_LIMITED`；用**无效 cid=0** 请求同样 429 → 限流维度是 IP/连接级，**与 cid 无关**。`/redeem-card` 8 次/2s、`/api/redeem` 8 次/2s → **无 429**。`/apply` 第 4 次起 **429 `rate_limited`**。
16. `/api/orders`：无 Key → 401；旧 Key（旋转后）→ 401「API Key 无效」；新 Key → 200，`customer_id=19`、`total=12`（全部自有单）。`limit=99999` → 被钳到 **100**；`offset=900000000` → 200，0.23s，无退化。
17. `/api/balance`：无 Key → 401；旧 Key → **200 `{"valid":false}`**；新 Key → 200 `{"valid":true}`（**不返回剩余积分**）。Key 大写变体 → `valid:false`；Key 尾随空格 → `valid:true`。
18. `https://62.106.70.167:60013` **TLS 握手失败**（`schannel: SEC_E_INVALID_TOKEN`）→ 该主机只有明文 HTTP。

## 5. 资损上界估算（100 积分 ≈ ¥1）

未找到「不付钱直接拿卡密」通道，可量化的白拿只有**新人额度**，且受 `/apply` 的 IP 限流节制：

| 通道 | 单次收益 | 放大系数 | 单 IP 上界 | 备注 |
| --- | --- | --- | --- | --- |
| 新 `device_id` → 100 新人积分 | ¥1 | 受 `/apply` 限流：实测同 IP 第 4 次即 429（窗口未知） | ≈ 3 × ¥1 = **¥3** | 换代理池可线性放大 |
| 大小写变体复用同一 `device_id` | ¥1 | 同上（仍受 `/apply` 限流节制，不受设备归一化限制） | ≈ 同上 | 一旦限流放宽，理论变体空间 2^32 |
| 双源各领一份 | ¥1 | ×2（池域 + apia 域各 100） | ≈ 3 设备 × 2 域 = **¥6** | 本条是与 #243 叠加后的实际上界 |
| 新人特惠 ¥1 → 500 积分 | 净赚 ¥4（面值 ¥5） | 需真实支付 ¥1/单；「已买过新人单能否再买」未测（缺支付） | 未确定 | #135 的核心；服务端下单层**不限制**重复创建 newbie 单（实测两次均 302） |
| 孤儿订单 | ¥0 直接资损 | 10 单/分钟/IP × 15 分钟有效期 | ~150 单/IP/窗口 | 资源与骚扰，非资损 |

**结论**：单 IP、单窗口的**可确认资损上界约 ¥6**（6 × 100 积分）；跨 IP 线性放大，上限由代理池规模决定。真正决定这个数字的是 `/apply` 的 IP 限流，而该限流的窗口/阈值在客户端不可见、也没有 `Retry-After`，属于「靠对手不知道」的防护（§8 建议改为设备维度 + 服务端持久指纹）。

## 8. 加固建议（P3，不拆单，建议随 #251–#255 修复时一并处理）

1. `usesCleartextTraffic` 改为 `false` + 白名单 `networkSecurityConfig`（只放行确需明文的测试域），并在邀请服务具备 HTTPS 后立刻切换。
2. 支付域（`apia.ecsafe.cn`）与邀请域都上证书固定（至少 pin 中间 CA 公钥 + 备用 pin）。
3. `/api/balance` 与 `/api/orders` 的鉴权失败口径统一：无效 Key 一律 401，不要一边 401 一边 200 + `valid:false`。
4. `/buy` 限流补 `Retry-After`，并把维度从纯 IP 改为 IP + 设备/cid 双维度。
5. `/api/order` 响应去掉 `customer_id`；`out_trade_no` 的随机段从 6 位 hex 提到 ≥16 位随机，消除存在性 oracle 的可枚举性。
6. `device.ts` 的 `Math.random` 兜底改为「拒绝生成 + 提示升级 WebView」，不要静默降级到弱随机。
7. `CheckoutBrowserPlugin.open()` 增加 host 白名单（只允许服务端下发的收银台域）并用 `createChooser`/`EXTRA_EXCLUDE` 限定浏览器；`resolveLocation()` 拒绝 `http://`。
8. 卡密兑换改为「先验 Key（或先验设备会话）再查卡」，把卡号存在性与凭据校验解耦，并给兑换链路加限流 + 失败计数退避。
9. 订单归属改为「按 Bearer Key 反查 customer_id」，`cid` 只作为展示/校验辅助，不作为唯一归属依据。
