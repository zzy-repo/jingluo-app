# ADR-0910：Native 端二进制原件（BLOB）放在哪里

状态：本期采纳（阶段性方案），长期方向见「退出条件」。日期：2026-11-26。关联：#906 #907 #910。

## 背景

- 9 个 store 里有两类二进制：聊天图片原件（`files`）与文档附件原件（`attachment-` 前缀，同属 `files` 键空间），另有 `appAssets`。
- `BlobRepo` 在接口层已声明「允许独立后端实例」（`storage/types.ts`），目的就是**故障隔离**：原件的体积、写失败、损坏不应拖垮不可再生的文本数据。
- 已发生的事故（IDB 在满盘 + 杀进程后被整库清空）说明：单一失败域里放得越多，一次故障丢得越多。
- 计划 D3 原先选择「分块 BLOB 存进同一个 SQLite 文件」。需要核对它与上述隔离目标是否冲突。

## 选项

| | A 单库分块 BLOB | B 文件系统存原件，SQLite 只存元数据 | C 独立的第二个 SQLite 文件放原件 |
|---|---|---|---|
| 与文本原子 | 同事务 | 两阶段（先落文件再写元数据），有孤儿窗口，靠清扫收敛 | 跨文件，无原子性 |
| 故障隔离 | 弱：库损坏文本与原件一起丢；大 BLOB 写满盘会和文本竞争空间 | 强：原件损坏/缺失不影响文本 | 中：库级隔离，但仍是 SQLite 文件 |
| `StagingRepo.commit/merge` | 保持现有原子语义 | 需重新定义（搬原件不在文本事务内） | 同 B |
| 备份 | `VACUUM INTO` 一次得一致副本，但体积 = 全部原件 | 文本备份很小，原件另备 | 同 B |
| 依赖 | 只依赖 SQLite 驱动 | 依赖 `AppFileSystem` 流式写入（现在只有 base64 整块过桥，5MB 级内存风险未验证） | 同 A 的驱动 |
| 迁移校验 | 一个库内对账 | 库 + 文件两处对账 | 两库对账 |
| 本期风险 | 库体积大、WAL 增长、迁移期磁盘 ×3 | 需先补流式 FS，改 Staging 语义，范围会扩大到 #907/#906 接口 | 同样要改 Staging 语义 |

## 决定

**本期采用 A，且明确它是阶段性选择，不是长期方案。** 理由：B/C 都要重新定义 `StagingRepo.commit/merge` 的原子语义（整包替换要把暂存原件搬进正式区，今天与文本在同一事务），并且 B 还依赖尚不存在的流式文件写入。在迁移这个「不允许丢数据」的节点上同时改事务语义，风险高于单库体积风险。

为了不让 A 把退出路径堵死，本期必须满足：

1. 原件的读写**只经 `BlobRepo`/`AssetRepo`/`AttachmentRepo`**，SQLite 内部集中在一个模块（`sqlite/blobStore.ts`），不允许别处直接碰分块表。
2. 元数据表预留存放位置列：`storage TEXT NOT NULL DEFAULT 'sqlite-chunks'`（将来可为 `'file'`）与可空的 `file_path`。只加列、不改现有列，升级是增量迁移。
3. 每个原件记录总长与整体 sha256，分块各带长度；读回必须校验，不符抛 `unavailable`，不返回残缺字节。
4. 块大小 ≤512KiB（Android `CursorWindow` 单行约 2MB 的上限，留余量），单次读写不整块进内存。
5. 迁移预检把原件体积按「源 + 备份 + 目标」三份计，磁盘不足不开始（见 plan §4）。
6. **文本的故障隔离靠 #909 的快照实现，不靠拆原件**：快照是应用私有目录里独立文件的瘦文本副本，不含原件；SQLite 库损坏时文本仍可从快照恢复。这是本期对「隔离目标」的实际兑现方式，它的覆盖范围与 RPO 由 Storage Reliability Suite E 项验收并写明。

## 与「独立 FileSystem 存储附件」的关系

不冲突，是同一条演进路径的两个阶段。`BlobRepo` 的接口不变，将来把实现换成「文件 + 元数据」即可，调用方与迁移引擎（按 `RawStoreSource/Sink` 读写）不用改。

## 退出条件（任一满足就重新评审，转 B）

- `AppFileSystem` 具备流式追加与校验写入，且在真机上验证过 ≥50MB 文件的内存与耗时；
- 真实或模拟的最坏数据集下，库文件 > 1GB，或 WAL 回写（checkpoint）单次耗时影响交互；
- Storage Reliability Suite 的 D 项显示「大 BLOB 写入」拖累文本提交的耐久性或延迟；
- 需要对原件做独立备份/清理策略（例如云端同步、按需下载）。

转 B 时必须另开 Issue，并重新定义 `StagingRepo` 的跨资源原子性（建议：先写原件、再写文本事务、孤儿清扫）。

## 已知代价（如实记录）

- 单库失败域：库损坏时原件与文本一起不可用，只能靠迁移备份与快照恢复文本；原件不在快照里，**不可恢复边界**：快照之后的文本、全部原件（图片与附件原文）。
- 库体积随原件线性增长，`VACUUM INTO` 备份体积同量级。
- 本决定未经真机验证，体积与 checkpoint 的结论来自 Node 与模拟器。
