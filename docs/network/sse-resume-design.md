# SSE 可续传（断流不丢内容）协议设计 —— #897

> 状态：**设计产出，未实现**。本文只定协议与两侧责任，不含客户端实现改动（#897 的关闭条件只到这一层）。
> 母单 #894「网络不可靠是基本假设」的第 3 条：**断流不该等于内容丢失**。
> 相关：`src/services/chat/streamBreakout.ts`（当前断流后的重试/丢弃口径）、
> `src/services/net/requestPolicy.ts`（`stream` 类的预算与重试语义）。

## 0. 今天断流会发生什么（为什么要这份设计）

流式生成的响应是一串 SSE 事件。连接一断，客户端手里只有**已经收到的前缀**，而「上游其实已经生成到第 N 段」
这件事只有服务端知道。当前口径（`streamBreakout.ts` 的表格）：

| 场景 | 今天的行为 | 用户感受 |
| --- | --- | --- |
| 首字节前断开 | 静默补试最多 5 次（同一请求重发） | 大概率无感 |
| 首字节后、内容 < 150 字 | 补 1 次，**丢弃半截**重来 | 已看到的字消失，重新开始 |
| 首字节后、内容 ≥ 150 字 | 不补试，软提示 + 「重新生成」 | **已生成的内容作废**，要么重看一遍，要么放弃 |
| 上游已生成完、事件没送到 | 同上 | 用户以为模型没答完 |

后面三行的共同点：**内容已经存在服务端（或上游）那边，但我们没有「从第 N+1 段继续」的手段**，
只能整段重来。整段重来的代价随回答长度线性增长，且计费重复。

所以 #897 要的是：**事件可编号 + 客户端能报「我收到哪了」+ 服务端能从那里接着发**。
三件事缺一件，续传就不成立（只加 `id` 不知道从哪续；只加 `resume` 参数没有序号对不上）。

## 1. 事件序号（`id` / `seq`）约定

### 1.1 线上形状

每个 SSE 事件**必须**带 `id:` 行（SSE 规范字段，浏览器 `EventSource` 会把它记成 `lastEventId`）：

```
id: 17
event: delta
data: {"text":"……"}

id: 18
event: delta
data: {"text":"……"}

id: 19
event: done
data: {"usage":{"prompt_tokens":812,"completion_tokens":240},"finish_reason":"stop"}

```

- `id` 是**十进制非负整数，单条流内严格 +1 递增，从 0 或 1 起（两侧约定一致即可，建议从 1）**。
- `id` 的唯一性范围 = **一次生成（一次 assistant 消息的产出）**，不是连接、不是会话。
- `data` 里**同时**放一份 `seq`（与 `id` 同值）。理由：`EventSource` 之外的通路（我们用的是 `fetch` +
  自读流，见 `src/services/chat/streamBreakout.ts` 的消费方式）读不到 `lastEventId`，
  只能从 `data` 里取；两份必须同值，任一侧缺失由一个断言挡住（见 §6）。
- **心跳不算事件**：`: ping` 注释行不带 `id`，也不占序号（否则序号会随心跳漂移，续传位置就对不上）。
- 事件类型固定四种，**只有 `delta` / `done` 携带「内容」**：

| `event` | 语义 | 续传时是否可重发 |
| --- | --- | --- |
| `delta` | 增量文本（正文 / 思考各一个字段，沿用现有 payload） | 可（从 seq+1 起） |
| `done` | 生成正常结束 + 用量 | 可（同一个 `done` 重发是幂等的） |
| `error` | 生成失败（终态） | 可（重发同一个 `error`，见 §5 错误码） |
| `meta` | 本次生成的元信息（模型、创建时间、是否可续传） | 只在首连发；续连时重发一次，便于客户端判断 |

### 1.2 `meta` 里必须有的两个字段

```json
{"event":"meta","seq":0,"data":{"resumable":true,"upstream_supports_resume":false}}
```

- `resumable`：这一次生成服务端**能不能**续（比如上游已经把生成结果落库 → `true`）。
- `upstream_supports_resume`：上游（真正的模型侧）是否原生支持续生成。`false` 时服务端走 §3.2 的降级，
  客户端据此决定文案（「已生成的部分已保留，可继续提问」而不是「正在续传」）。

## 2. `Last-Event-ID` 语义

续传请求复用**同一个**对话补全接口，通过请求头声明「我收到哪了」：

```
POST /v1/chat/completions
Accept: text/event-stream
Last-Event-ID: 18
X-Resume-Generation: 7f3c…（可选，见 §2.2）
```

规则：

1. **`Last-Event-ID` = 客户端成功解析并已展示的最后一个事件的 `id`**。服务端从 `id + 1` 开始发。
2. 客户端**只认已落进 UI 的事件**：收到但没渲染的不算（否则用户会丢那一段）。
   `id` 跳号（中间丢了一个）时，客户端必须报**最后一个连续的** `id`，不能报最大的 ——
   否则中间那段永久丢失（服务端以为客户端有了）。
3. 请求头缺失 = 全新生成（今天的行为，逐字不变）。
4. 请求头非法（非整数 / 负数 / 超出该次生成的已知范围）→ **`400 invalid_last_event_id`**，
   不要静默当成「从头开始」（静默从头 = 用户看到重复内容，且可能重复计费）。
5. `id` 只在**同一次生成内**有意义。跨生成复用没有语义，服务端必须用「生成标识」把两者绑起来（§2.2）。

### 2.1 为什么用请求头而不是 query

- 与 SSE 规范的 `Last-Event-ID` 同名同义，`EventSource` 自动带、`fetch` 手带一行，不需要额外协议；
- 不落 URL（不产生「带状态的 URL 被分享 / 被日志完整记录」问题）；
- 网关侧更容易按头做透传与限流分类。

### 2.2 生成标识（`X-Resume-Generation`）

`id` 是「这次生成的第几段」，但客户端还需要说清「续的是**哪一次**生成」。两种可选形态，二者取一（待定，见 §7 Q1）：

- **A（推荐）**：首连的 `meta` 事件里给 `generation_id`，续连时客户端把它放进 `X-Resume-Generation`。
  服务端据此找回缓存 / 落库的产出，不依赖「同一个 JWT + 最近一次生成」这种隐式约定。
- **B（省一个头）**：把 `generation_id` 编进 `id`（`id: <gen>:<seq>`），`Last-Event-ID` 自带标识。
  代价：`id` 不再是纯整数，某些 SSE 中间件会假定它是整数（我们自己的网关也要改）。

A 的代价是多一个头，B 的代价是 `id` 不纯。**建议 A**：网关只需要「放行一个自定义头」，不必解析 `id` 语义。

## 3. 服务端从 `seq + 1` 续发

### 3.1 可续的条件（全部满足才续）

1. `X-Resume-Generation` 能找到对应的一次生成记录；
2. 该生成**还在保留窗口内**（建议 ≥ 10 分钟，与客户端 `stream` 类的总预算同量级）；
3. 已知产出是**有序可索引**的（服务端按 `seq` 存了分段，而不是只存一个拼好的字符串）；
4. 该生成没有被取消 / 没有因错误终结（终态的不续，直接重发 `error` 或 `done`）。

满足时：先发 `meta`（带 `resumable: true`），再从 `seq+1` 起把**已有的**分段按原样重放，然后
继续转发上游的新分段。序号必须**与首连完全一致**（同一段内容在两次连接里的 `id` 必须相同，
否则客户端会拼出重复或错位）。

### 3.2 上游不支持续话时的降级（`upstream_supports_resume: false`）

绝大多数上游不支持「从第 N 个 token 继续生成」，所以续传的现实形态是**分级降级**，而不是「无缝续写」：

| 情形 | 服务端做什么 | 客户端看到 |
| --- | --- | --- |
| 生成**已结束**（上游已发完，只是最后一段没送到） | 把完整产出按 `seq+1…N` 补发，再发 `done`（含原用量） | **内容完整**，用户只感到「卡了一下」。这是最值钱的一档 |
| 生成**未结束**且服务端缓存了已收到的分段 | 补发已缓存分段（到 `seq_cached`），再发 `resume_end` 说明后续不可续 | 已生成部分**保留**，明确告知「上游已断开，无法继续生成」，给「重新生成」按钮 |
| 生成**未结束**且没有任何缓存 | 不续：`meta`（`resumable:false`）→ `error`（`upstream_disconnected`） | 明确一句「这条回答没能生成完」，已收到的不丢（客户端不清空） |

关键纪律：**降级时绝不假装成功**。补发了多少就说到多少，`done` 只在真的完整时才发。
不允许「补一半 + done」—— 那会让界面显示「完成」而内容其实是残的（比报错更糟：用户不知道要重问）。

### 3.3 续传不得重复计费

- 补发的分段是**已计费产出**的重放，不得再计一次（用量只在 `done` 里给一次，且是这一次生成的总量）；
- 客户端在续连时不重置本地用量显示，等 `done` 覆盖。

## 4. 兼容旧客户端

| 客户端 | 行为 |
| --- | --- |
| 老客户端（不认识 `id` / `meta` / `resume_end`） | 服务端**始终**照旧发 `delta` / `done` / `error`；`id:` 是 SSE 规范字段，老客户端忽略它不受影响；`meta` / `resume_end` 是**新增 event 名**，老客户端按「未知事件类型」忽略即可（今天 `streamBreakout.ts` 对未知 event 就是跳过）。**不允许**为了新协议改动 `delta` / `done` 的 payload 形状 |
| 新客户端 + 老服务端（没升级） | 请求里带了 `Last-Event-ID` 但服务端不认识 → 服务端按「全新生成」处理（HTTP 层不该 400）。客户端必须在**首连 5 秒内没等到 `meta`** 时降级为「不可续」模式，绝不因为续传能力缺失而让发送失败 |
| 新客户端 + 新服务端 | 走 §3 |

**顺序纪律**：先让服务端在**不需要新客户端**的前提下发 `id` 与 `meta`（老客户端不受影响、可以先上），
再让客户端在**不需要新服务端**的前提下带 `Last-Event-ID`（服务端不认识就当全新生成、也不受影响）。
两侧各自的降级路径独立成立，才允许分开上线。

## 5. 错误码（续传相关）

| HTTP | 机器码 | 含义 | 客户端该做什么 |
| --- | --- | --- | --- |
| 400 | `invalid_last_event_id` | `Last-Event-ID` 不是合法整数 / 越界 | **不要静默重发**：按「全新生成」重发一次，并在诊断里记一条（出现即说明两侧序号语义不一致） |
| 404 | `generation_not_found` | `X-Resume-Generation` 找不到（过期 / 从没存在 / 换设备） | 降级为「不可续」：保留已收到内容，软提示 + 「重新生成」 |
| 409 | `generation_finished` | 该生成已经结束且已完整送达过 | 视为成功：不要再生成一次（避免重复计费） |
| 410 | `generation_expired` | 超出保留窗口 | 同 404 |
| 429 | `Retry-After: <秒>` | 上游限流 / 网关限流 | 按 `Retry-After` 退避（`requestPolicy.ts` 的 `backoffOf` 已优先读它），**不是**终态 |
| 503 | `upstream_disconnected` | 上游中途断开且不可续 | 保留已收到内容 + 明确文案 + 「重新生成」 |

SSE 内的终态错误（连接已建立、中途失败）沿用 `event: error` + `data.code`，码表与上表同一份
（避免「头里一个码、事件里另一个码」两套口径）。

网关侧纪律：**`Retry-After` 必须透传**（今天若有中间层丢弃它，客户端只能瞎猜退避，表现为「越抖越糟」）。

## 6. 两侧各自怎么被证伪（不然这份设计等于没写）

| 判据 | 怎么测 | 放哪一层 |
| --- | --- | --- |
| `id` 与 `data.seq` 同值、单条流内严格 +1、心跳不占号 | 逐事件断言 | 服务端单测 |
| 客户端只报「最后一个连续 id」 | 构造跳号流，断言上报值 | L0（纯函数：从事件数组算 resumeFrom） |
| 补发后内容**不重复、不缺口** | 首连收到 1..18 → 断开 → 续连收 19..N → 拼起来的字符串与「一次收完」逐字相同 | L1（mock 上游） |
| 降级三档各自的行为 | `upstream_supports_resume=false` 下的三种缓存状态各一条 | 服务端单测 + L1 |
| 老客户端不受影响 | 用不认识 `meta` 的消费路径跑一遍 | L0（未知 event 跳过） |
| 少一件也能上线 | 服务端先发 `id`（客户端不读）、客户端后带 `Last-Event-ID`（服务端不认） | 各自独立验证 |

**没有验收判据的设计不接线**：上面每一条都要有一个会真正红的用例，否则「可续传」只是文档里的说法。

## 7. 后端需要做什么（`felix4396/sub2api-private`）

按**依赖顺序**排，前一项不做后一项没有意义：

1. **SSE 事件加 `id`**：`delta` / `done` / `error` / `meta` 逐事件带 `id: <seq>`，`data` 里同时带 `seq`；
   心跳 `: ping` 不占序号。← **这一步单独就能上**（老客户端无感）。
2. **`meta` 事件**：首连发一次，含 `generation_id`、`resumable`、`upstream_supports_resume`。
3. **接受 `Last-Event-ID` + `X-Resume-Generation`**：合法则从 `seq+1` 续发已缓存分段；非法按 §5 回码。
4. **分段有序缓存**：把已产出分段按 `seq` 存起来（内存 + 落库皆可，保留窗口 ≥ 10 分钟），
   而不是只存拼好的整串 —— 没有序号索引就续不了。
5. **生成终态落库**：上游结束后即便连接已断，产出与用量要能补发（§3.2 第一档，最值钱）。
6. **网关透传 `Retry-After`**，并放行自定义头 `X-Resume-Generation`（CORS 的
   `Access-Control-Allow-Headers` 也要加，否则 web 端预检直接失败）。
7. **错误码**：按 §5 的 http/码表实现（400 / 404 / 409 / 410 / 503）。

## 9. 后端 issue 正文（可直接粘贴）

> 若 `felix4396/sub2api-private` 的 token 无权限建单，用这段在那边手动创建，标题用下面第一行。

**标题**：`[SSE] 事件加序号 + 支持 Last-Event-ID 续传（配合前端 #897 / 母单 #894）`

**正文**：

前端正在把「网络不可靠」当作基本假设（母单 #894）。其中一条是**断流不丢内容**（前端 #897）：
现在连接一断，客户端只有已收到的前缀，「上游其实已经生成到第 N 段」只有服务端知道，
于是只能整段重来 —— 用户看到的内容作废，上游重复计费。

**请后端做（按依赖顺序）：**

1. SSE 每个事件带 `id: <seq>`（十进制整数，单条流内严格 +1），`data` 里同时放 `seq`（同值）；
   心跳 `: ping` 不占序号。
2. 首连发一次 `event: meta`，含 `generation_id` / `resumable` / `upstream_supports_resume`。
3. 接受请求头 `Last-Event-ID`（= 客户端已展示的最后一个 `id`）与 `X-Resume-Generation`，
   从 `seq + 1` 起补发已缓存分段，然后继续转发上游新分段；两次连接里**同一段内容的 `id` 必须相同**。
4. 分段**按 seq 有序缓存**（保留 ≥ 10 分钟），不能只存拼好的整串。
5. 生成结束后即便连接已断，产出与用量仍要能补发（这是最值钱的一档：内容完整、用户只是「卡了一下」）。
6. 网关透传 `Retry-After`，并在 CORS `Access-Control-Allow-Headers` 里放行 `X-Resume-Generation`。
7. 错误码：`400 invalid_last_event_id` / `404 generation_not_found` / `409 generation_finished` /
   `410 generation_expired` / `503 upstream_disconnected`。

**兼容要求（很重要）：** 老客户端不认识 `meta` / `id`，必须照样能用 —— 建议服务端**先**上线第 1 步
（只加 `id`，不改 `delta`/`done` 的 payload），前端**后**上线带 `Last-Event-ID`；两步各自可独立回滚。

**验收判据：** 首连收到 1..18 → 断连 → 续连收 19..N，拼起来与「一次收完」逐字相同；
`upstream_supports_resume=false` 时降级为「补发已生成部分 + 明确说明」，不得补一半就发 `done`。

设计全文见前端仓库 `docs/network/sse-resume-design.md`（含待确认清单 Q1–Q7）。
