# 服务端地址迁移台账（#181）

> 回答三个问题：**这块地址搬过几次？这次怎么搬的？旧机下线那天用户会看到什么？**
> 客户端侧改动在 PR #186（已合并 `fab625b`），决策与实测记录在
> [#181](https://github.com/zzy-repo/deepseek-app/issues/181)。本文是**发布/运维视角**的那份。

## 1. 三代地址

| 代 | 地址 | 写入版本 | 端口 | 现状（2026-11-18 实测） |
| --- | --- | --- | --- | --- |
| 第一代 | `123.207.199.196` | beta.5 之前的 Anthropic Messages 上游 | 60010 | 已下线 |
| 第二代 | `62.106.70.167` | beta.8 及之前 | 60010 对话 / 60012 反馈 / 60013 邀请+额度 | **仍在线**，待下线 |
| 第三代 | `140.210.13.146` | beta.9 起（PR #186） | 同上三端口 | 在线，契约已实测 |

三个端口**都没有域名，全是明文 HTTP**，靠 Android 壳的 `usesCleartextTraffic="true"` 才能用。
地址写死在客户端里（`providers.ts` 的 `ours.defaults`、~~`invite/api.ts`~~ 的 `INVITE_API_BASE`（#604 已删，邀请 / 卡密迁到 `src/services/consume/`）、
`diagnostics/config.ts` 的 `LEGACY_FEEDBACK_URL`），所以每次搬机器都等于**再发一次版**。

## 2. 过渡策略：**C —— 旧机下线，强制升级**

已定：**旧 IP 不做长期兼容**。等新版铺开，直接下线 `62.106.70.167`，用「老版本连不上」把存量版本逼上最新版。
本单只落客户端侧（改地址 + 老用户本地旧地址迁移 + 构建期写死 IP 检查），下线动作在后端/运维侧，不走本仓库代码。

### 2.1 必须如实写出的风险

- **已发布的 beta.8 及更早版本会整体不可用**，不是某一个功能降级：对话打不开、邀请/领卡/换 Key 全挂、反馈也发不出来（三端口同机）。
- **用户看到的不是「请升级」，而是网络错误 / 一直转圈 / 请求失败。** 因为那些版本里**没有任何版本检查逻辑**，也没有「服务端地址」这种可远程改的配置项——地址是编译期常量。
  老版本没法被「告知」什么，它只会一次次打一个已经没人听的端口。
- 因此**强制升级这件事，目前只能靠「用不了」来强制**，不靠提示。这在体验上是硬中断，会有一批用户以为是 App 坏了、或者以为是自己网络问题，跑去给差评/发工单。
- 这类投诉**无法由客户端侧缓解**：改不了已发出去的包。

### 2.2 缓解建议（后端动作，**不阻塞发布**，但必须让运维看到）

**在旧机真正下线之前**，让旧 IP 上的三个端口先返回一个**人能看懂**的「请升级」响应，跑满一段窗口期：

| 端口 | 建议行为 |
| --- | --- |
| `:60010` 对话网关 | 对所有请求（含 `POST /v1/chat/completions`）返回**可读文本 + 非 2xx**，例如 `503` 带 `{"error":{"message":"服务已迁移，请升级 App 到最新版本（设置 → 检查更新）"}}`。**关键是这句话要能透到界面上**——客户端把上游错误正文当提示渲染的路径存在，纯 502 空体会退化成「网络错误」。 |
| `:60012/feedback` 反馈 | 返回 `200 {"ok":true,...}` **不算数**（用户以为自己反馈成功了，其实没人收）；应返回 `4xx/5xx` + 同样的升级文案，至少让「反馈失败」这件事看起来是服务端的问题而不是用户的问题。 |
| `:60013` 邀请/额度 | 同上，`503` + 升级文案；别返回 `404` 之类会被客户端当成「本机没领过 Key」的业务码（见 `rotate.ts` 的 `device_not_found` 分支），那会诱导用户重新领取/换 Key。 |

窗口期**至少覆盖到下一次正式发版之后**（即：新版本已经能下载、且有足够时间让活跃用户更新），再由运维停机。

**为什么这条重要**：这是唯一能在「老版本没有任何升级提示能力」的前提下，让用户看懂发生什么了的办法。
本单不实现它（后端动作），但**下一次发版的 release notes 必须写进这一条**，否则运维只会看到「换个 IP」四个字就把旧机停了。

### 2.3 不在本单做的（别误会）

- **不新增版本检查 / 强制升级弹窗**：那超出 #181 的范围，是个独立功能（拉版本号、比版本、弹不可关闭的层、跳更新页）。
  #181 的关闭条件只要求「写明策略并在发布说明体现」。
- 但要说清楚：**不做版本检查，就谈不上真正意义上的「强制升级」**——现阶段「强制」= 老版本直接连不上。
  想让用户体验到「请升级」，要么走上面 2.2 的后端兜底响应，要么另开一单做客户端版本检查。

## 3. 前向建议：下次迁移前先配域名

这已经是**第三次**因为服务器变动而改写死 IP：`123.207.199.196` → `62.106.70.167` → `140.210.13.146`。
每来一次，代价都是「改代码 + 全量回归 + 老用户本地脏数据迁移 + 再发一次版 + 老版本彻底不可用」。

下次搬机器之前，建议先做掉这两件事，然后**地址一次改成域名**（之后同域换 IP 不需要发版）：

1. 三个端口配域名（哪怕是二级域名），并上 **HTTPS**（顺带解决明文 HTTP 的安全问题，以及 WebView 混合内容/未来 Android 限制）；
2. 客户端只保留域名常量（现在有 `pnpm check:ip` 兜着，见 `scripts/check-hardcoded-ip.mjs`，新增写死 IP 会直接挂门禁）。

## 4. 客户端侧这次做了什么（细节在 PR #186）

- 三处地址换成 `140.210.13.146`；`rotate.ts` / `bind.ts` 主链路派生自 `INVITE_API_BASE`，只同步注释；
  支付域名 `https://apia.ecsafe.cn` 与两个 `/invite/*` 兜底地址**按 issue 要求不动**。
- **老用户迁移**：`apiConfig.ts` 的 `LEGACY_HOSTS` 收了 `123.207.199.196` 与 `62.106.70.167`，`storedBaseUrl()`
  读到即当「没配过」回落内置默认（补的是 1.2.2 内测用户那份共享 `chat-demo:base-url` 的坑），自填地址不受影响。
- **防复发**：`scripts/check-hardcoded-ip.mjs`（`pnpm check:ip`）扫 `src/` `scripts/`（`repro/` 已在 #291 删除），
  公网裸 IP 直接 exit 1；`140.210.13.146` 在 `ALLOWED_HOSTS` 里显式豁免，确需保留字面量的行用 `check-ip-allow` 标注。
- **契约实测**（宿主侧，非 E2E）：`:60010` 未知路径回 `{"error":{"type":"not_found_error",...,"code":"unknown_api_path"}}`（404）；
  `:60012/feedback` 最小合法体回 `{"ok":true,"id":"<uuid>",...}`（200）；`:60013/rotate` 带不存在设备码回
  `{"error":{"code":"device_not_found","message":"apply for a key first"}}`（404）——路由与协议都没变。
